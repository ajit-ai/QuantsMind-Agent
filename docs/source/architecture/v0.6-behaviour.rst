================
v0.6.0 behaviour
================

Three capabilities that existed but had no consumer are now reachable: verifying
a finished task, falling back to another model endpoint when that is safe, and
asking for JSON-shaped output. This page describes what they do and, where the
difference between two similar things matters, which one this is.

Verification
============

When a task verifies
--------------------

A task is verified when its plan carries acceptance criteria. Those criteria are
generated by the application, not proposed by the model, so this is a promise the
application made about itself. A plan with no criteria completes exactly as it
did before verification existed: steps run, task completes, no check runs.

Sequence for a task that promised evidence::

    steps execute one at a time
        -> every step succeeded
        -> the task parks in VERIFYING  (not COMPLETED)
        -> checks are discovered from the workspace and run
        -> one verdict is recorded
        -> the task settles on that verdict

The park matters. Settling to ``COMPLETED`` and verifying afterwards would report
"verified" about a task nobody had checked at the moment anyone might be looking.

Three verdicts
--------------

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - Verdict
     - Established
   * - ``pass``
     - Every criterion has a passing check that names it
   * - ``fail``
     - A check ran and failed
   * - ``inconclusive``
     - A check could not run, was refused by command policy, timed out, or the
       project declares none

Inconclusive is not a softer pass. It is the answer "we could not tell".

A task whose checks all passed still settles inconclusive when no passing check
names its criteria. Green tests that do not speak to the criteria are not evidence
about them.

.. list-table::
   :header-rows: 1
   :widths: 30 35 35

   * - Verdict
     - Task settles as
     - Why
   * - ``pass``
     - ``completed``
     - The promise was kept
   * - ``fail``
     - ``failed``
     - There is evidence the criteria were not met
   * - ``inconclusive``
     - ``blocked``
     - Stopped, waiting for a decision -- not a failure of the work, and not a
       success

No new task states were introduced. ``VERIFYING`` and ``BLOCKED`` already existed
and already mean exactly this.

What verification may not do
----------------------------

* It does not widen the plan, the workspace or the scope. Checks are classified by
  the same command policy that classifies every other command, and a refused check
  is recorded as blocked, which makes the task inconclusive -- never a pass.
* It does not run without an approved plan. A rejected or unapproved task cannot
  verify at all.
* It does not buy a fresh budget. The check budget and the active-time budget
  apply, and a task whose time budget is already spent settles inconclusive.
* It does not run on the GUI thread. It runs where the task runs, because it runs
  the project's test suite.
* A recorded verdict is never overwritten by a second run.

Recovery
--------

A task interrupted *during* verification is interrupted, like any other work in
flight. It is reported as interrupted, its outcome is unknown, and it is not
resumed automatically. The recorded verdict, if one was written, survives.

Provider routing and fallback
=============================

A router is built only when routing is configured *and* has somewhere to go. With
one endpoint no router exists, and an unconfigured feature that moves a request to
a different service is not a safe default.

The order written in the configuration is the order used, and it is never
reordered at runtime.

What may move to another endpoint
---------------------------------

.. list-table::
   :header-rows: 1
   :widths: 45 20 35

   * - Failure
     - Falls back
     - Why
   * - 429 rate limit
     - Yes
     - The request was refused before any work
   * - 5xx server error
     - Yes
     - Same
   * - 401/403 authentication
     - No
     - The same bad key fails the same way elsewhere; moving hides it
   * - 404 model or endpoint
     - No
     - A configuration mistake, not a transient fault
   * - Timeout after sending
     - No
     - The provider may have finished the work and lost the response
   * - Connection failure
     - No
     - Same ambiguity
   * - Protocol error
     - No
     - The endpoint answered; it answered wrongly

Attempts are bounded by ``routing.max_attempts`` (1-5, default 2), and the
original failure is raised when nothing serves.

Capabilities are the intersection across endpoints, not the union: routing to an
endpoint that cannot stream would break a caller that asked for streaming.

Each attempt is recorded as endpoint, model, outcome and failure kind. No prompt
and no credential is recorded -- the routing log is meant to be readable in a bug
report.

Configuration::

    [routing]
    enabled = true
    max_attempts = 2

    [[routing.fallbacks]]
    base_url = "http://localhost:11434/v1"
    model = "qwen2.5-coder"

Structured output
=================

A request carries a schema; the response carries the parsed data and which
guarantee was obtained.

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Stage
     - Behaviour
   * - Capability
     - The endpoint must declare structured-output support. If it does not, the
       gateway refuses the request with an explanation rather than returning
       prose the caller has to guess the shape of.
   * - Guarantee
     - ``native`` when the provider constrained the output; ``parsed`` when the
       application extracted it from prose. Both work. They are different promises
       and the response records which one applied.
   * - Validity
     - The schema is validated by this application, every time, whichever path
       produced the data. A constrained answer is re-checked, not trusted.

Failure is explicit
-------------------

Malformed, truncated or off-schema answers raise ``StructuredOutputError``. They
do not become an empty result: "the model returned nothing usable" and "the model
returned a valid empty answer" must not look identical, and an empty plan would
otherwise be indistinguishable from a successful one.

JSON inside a fenced block is accepted, because models fence JSON as a
formatting habit. JSON inside a paragraph is refused, because scanning for where
the JSON starts is how a plausible answer gets accepted from a wrong one.

The supported schema subset is small -- object, array, string, number, integer,
boolean and null, with ``required``, ``properties``, ``items`` and ``enum``. The
guarantee that matters is not breadth; it is that the application can re-check
what it received without trusting the provider to have constrained it.

Requests that do not ask for structured output are unchanged: no ``response_format``
is sent and no parsing happens.

Persistence
===========

Task records moved to schema version 2, which adds ``verification``. A record
written by an earlier version loads with no verdict, which reads as *never
verified* -- not as *verified by an absence of evidence*. A record claiming a
newer schema is refused rather than reinterpreted.

Security notes
==============

* Verification commands are classified by the same command policy as every other
  command; a refused check makes the task inconclusive, never successful.
* Fallback never bypasses configured policy: a fallback endpoint is an endpoint the
  user configured.
* Structured output is untrusted input. It is parsed and validated before use and
  is never interpreted as instructions.
* Attempt records and structured-output errors carry no prompt text and no
  credential.
