=========================================
v1.0.0 readiness qualification: v0.9.0
=========================================

.. contents::
   :local:
   :depth: 2

This is a qualification record, not a release approval. It asks two separate
questions:

#. Is the published v0.9.0 artifact fit for real-world use?
#. Is the evidence sufficient to start v1.0.0 as a stable release?

The answers are different. The artifact is fit for a **supervised technical
beta** on Windows 11 x64. It is **not** fit for general distribution or a
v1.0.0 stable claim on the evidence available.

Verdict
========

**CONDITIONAL -- LIMITED BETA ONLY**

The v0.9.0 MSI installs, launches, survives a reinstall, uninstalls cleanly,
and leaves the real user profile byte-identical. The packaged application and
the source suite pass their automated gates. Core workspace-intelligence and
task-evidence behaviour is covered by acceptance fixtures and regression tests.

That is enough to put the build in front of supervised technical testers on
disposable projects. It is not enough to call v0.9.0 generally usable, and it is
not enough to open v1.0.0.

The limiting facts are:

* no request has been sent to a real model provider;
* no human has reviewed the rendered desktop interface or driven an approval
  dialog;
* no clean machine or independent installer has been tested;
* the MSI and executable are unsigned, and no signing key or trusted-publisher
  process exists in this repository;
* a directory junction inside a workspace breaks discovery in the published
  v0.9.0 artifact (fixed in the source tree, pending release retest);
* current user and security documentation described v0.1/v0.2 behaviour at the
  assessment cut-off (corrected in source on 2026-10-21; see below);
* the release-commit CI signal is not available;
* the 0.9-to-1.0 upgrade path has not been tested.

The detailed open items are in :doc:`defect-triage`. The executable beta
procedure is in :doc:`manual-beta-acceptance`.

QF-006 / G23: root cause and correction
---------------------------------------

The walk used ``os.walk(..., followlinks=False)``. On Windows that flag does
not suppress directory junctions: a junction is reported as a directory and is
descended. The listing path then resolved the junction target and
``_relative_of`` correctly refused the outside path, but the refusal escaped as
an unhandled ``InvalidPathError`` and failed the whole scan.

The corrected policy is explicit:

* discovery never follows symbolic links, junctions or other filesystem
  reparse points;
* listings and walks omit them, and the walk can return their
  workspace-relative paths as excluded entries;
* the workspace snapshot records the excluded paths in ``unknowns`` rather than
  claiming complete coverage;
* direct reads through an outward link remain refused by path containment;
* an entry-budget, sampling or ignored-directory decision is unchanged.

The change is in :mod:`quantsmind_agent.workspace` and
:func:`quantsmind_agent.workspace_intel.discover_workspace`. The snapshot schema
was not changed; the exclusion is carried in the existing ``unknowns`` field.

G25 / QF-001: signing requirement
---------------------------------

The signing guide and verifier remain unmerged on
``release-engineering/post-v0.8.0`` at ``aede81b``. There is still no production
certificate, timestamping service, HSM-backed key or trusted-publisher
credential. The required future sequence is:

#. sign ``QuantsMindAgent.exe`` before building the MSI;
#. sign the MSI and apply a trusted timestamp;
#. verify both with ``signtool verify /pa`` and record the signer subject;
#. publish a new version, tag and artifact; never re-sign or replace v0.9.0;
#. stop the release if a trusted signing path is unavailable.

A self-signed certificate is not production trust. G25 remains open.

Scope and non-claims
====================

This assessment covers the **published Windows 11 AMD64 v0.9.0 MSI** and the
matching onedir build. It does not cover:

* Linux, macOS or BSD;
* a v1.0.0 artifact, which does not exist;
* source installations;
* a security audit, penetration test, or operating-system sandbox;
* model quality, provider billing, or provider data-handling terms;
* accessibility, localisation, or high-DPI review by a person;
* multi-user deployment, roaming profiles, or enterprise management.

No result here proves that an answer from a real model is correct. The automated
suite proves the application's own boundaries and contracts; it does not prove
model judgement.

Detailed findings
=================

Artifact and installer
----------------------

The artifact is internally consistent and the installer behaves correctly in
the tested same-user configuration. It installs per-user without elevation,
creates working shortcuts, registers one installed-apps entry, launches a real
window, and removes all of those on uninstall. Reinstall repairs the installation
without duplicating files or registry entries. The real user profile is left
byte-identical.

This is strong installer evidence, not clean-machine evidence. The build host
already had the source tree, Python, build tools, and the user's credential store.
A clean VM is still required to prove first-run dependencies and the genuine
SmartScreen experience.

The artifact is unsigned. Windows SmartScreen warnings are expected and are a
trust problem, not an application crash. A hash published over a trusted channel
reduces accidental substitution but does not establish publisher identity.

Workspace intelligence
----------------------

The v0.9.0 snapshot contract behaved as documented on the acceptance fixtures:

* Python package: ``python-package``, confidence 0.88, source/test/doc roots,
  and a declared pytest check that passed;
* Node package: ``npm-lint`` and ``npm-test`` discovered from declared scripts;
* polyglot: Node plus Rust, with both declared checks;
* unknown project: no invented checks, three explicit unknowns, confidence 0.0;
* large project: 450 files, 400 sampled, ``sampled=true``,
  ``truncated=false``, ``complete=false``.

The prompt rendering omitted the absolute workspace path and stayed bounded. A
snapshot stored on a task survived persistence and reload. The snapshot is
evidence, not authority: approval still binds to the plan digest and the
workspace policy.

The junction failure is the one functional regression found in this area. A
workspace containing a directory junction to an outside directory makes
``Workspace.walk`` and ``discover_workspace`` raise ``InvalidPathError`` instead
of producing a partial or explicitly incomplete snapshot. Direct reads through
the junction are correctly refused. The GUI worker catches the exception and
emits a scan failure, so the likely user-visible result is a failed project scan,
not a crash or data escape. Projects that use junctions -- including some
dependency layouts and Windows development setups -- can hit this without any
malicious intent. See :doc:`defect-triage`.

-------------

No result contained the test key, and the product log files did not contain it
or an ``Authorization`` header. A real provider is still required to test model
tool selection, answer quality, streaming latency, and provider-specific error
bodies.

Security boundary
-----------------

The deterministic acceptance checks confirm the important refusals:

* a stale edit is rejected and the file remains byte-identical;
* a command blocked by policy is never offered for approval and never runs;
* an approved benign command runs and returns real output;
* a traversal write is refused and the outside file remains untouched;
* permitted write, edit and delete operations still work.

The application remains application-level containment, not an OS sandbox. A
model can still be misled by repository content; there is no prompt-injection
detector. Logs contain paths, prompts and error details. Those limits must be
stated plainly to beta testers.

--------------------------------

surrounding product documentation was not: the index said Version 0.2, the

The v0.9.0 package workflow was still queued at the evidence cut-off. A separate

The signing guide and fail-closed verification script exist on

Conditions for a limited beta
=============================

The verdict is conditional on all of the following:

#. **Distribution is controlled.** Provide the MSI only with its SHA-256 through
   a channel the tester already trusts. Do not present it as a v1.0.0 candidate.
#. **The tester is technical and supervised.** The beta is for developers who
   can recognise a failed scan, an approval prompt and a provider error, and who
   will preserve evidence.
#. **The project is disposable.** Use a non-sensitive repository or the
   acceptance fixture, with a backup or clean Git state. Do not point the beta at
   production, credentials, customer data or a repository that cannot be
   restored.
#. **The credential is revocable.** Use a dedicated key with a low limit, enter
   it through Settings, and revoke it after the test.
#. **Junctions are excluded from the published beta.** Do not use a workspace
   containing a directory junction to an outside location with the published
   v0.9.0 MSI. An internal candidate contains and passed the fix, but it is not
   approved for external beta. This is a documented beta limitation, not a
   supported configuration.
#. **Unsigned-build risk is explicit.** Testers must expect SmartScreen and
   security-software warnings; a block or quarantine is a trust finding, not a
   silent retry.
#. **Evidence is captured.** Record the artifact hash, machine, provider/model,
   test ID, outcome and a scrubbed log excerpt. Never record a key, prompt with
   secrets, or a full production path.
#. **Stop conditions are honoured.** Stop on any read outside the workspace, an
   approval bypass, a key in the UI or logs, data loss, install/uninstall damage,
   or a crash while an approval is pending.

Passing the beta plan does **not** by itself make v1.0.0. It supplies the
human, real-provider and independent-machine evidence that is currently absent.

Conditions for v1.0.0
=====================

At minimum, close the following before a v1.0.0 release:

* resolve QF-001 signing and trusted publishing;
* complete QF-002 real-provider qualification;
* complete QF-003 human GUI and approval acceptance;
* complete QF-004 clean-VM independent installation;
* obtain QF-005 external beta evidence;
* ship a candidate containing the QF-006 junction fix and repeat the junction
  test against that exact artifact;
* correct QF-007 user and security documentation;
* obtain QF-008 a green CI run on the release commit;
* qualify QF-009 the 0.9-to-1.0 upgrade path;
* complete QF-010 long-session evidence or state a tested session limit.

The full triage, severity and close-out criteria are in
:doc:`defect-triage`.

Residual risks
==============

These risks remain even if every automated gate passes:

* **Prompt injection.** Repository text is data, but it can still mislead the
  model. There is no injection classifier.
* **Command policy is not a sandbox.** The deny-by-default policy is enforced by
  the application process, not the operating system.
* **Logs are sensitive.** They contain paths, prompts and error details and are
  not encrypted.
* **No code signature.** Users cannot verify publisher identity from the file
  alone, and security software may block it.
* **Bounded snapshots.** The project view is sampled and may be incomplete;
  consumers must read ``complete``, ``truncated`` and ``sampled``.
* **No update mechanism or telemetry.** There is no automatic patching and no
  fleet-level crash reporting.
* **Junction limitation in the published artifact.** The published v0.9.0 MSI
  can fail discovery on a workspace containing an outward junction. The source
  fix excludes links from discovery and reports them as unknown. The internal
  candidate contains the fix and passed artifact-level G23; the published
  artifact is unchanged. Any public release must rebuild and retest it.
