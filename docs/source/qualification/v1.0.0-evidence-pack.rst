===========================================
v1.0.0 human-gate evidence pack (templates)
===========================================

.. contents::
   :local:
   :depth: 2

**Execution status: NOT TESTED.** This document contains blank recording
templates for the human and external gates in :doc:`defect-triage`. It is not
evidence. Do not copy a row into a release report as ``PASS`` unless the named
reviewer has observed it and the supporting record exists.

The detailed *how to test* procedures already exist:

* :doc:`manual-beta-acceptance` -- the Windows 11 beta plan, fixture and safety rules.
* :doc:`../testing/native-gui-acceptance` -- the native GUI checklist (QF-003).
* :doc:`../testing/live-provider-validation-v0.5` -- provider test ideas (QF-002).

This pack is the *what to record* layer: a consistent identity block per run and
one result table per gate, so that evidence from different testers is comparable
and can be triaged.

Scope and status vocabulary
===========================

Use the vocabulary in :doc:`index`: ``PASS``, ``FAIL``, ``BLOCKED``,
``NOT TESTED``, ``NOT APPLICABLE``. A queued job is not a pass; a local stub is
not a real provider; an automated window check is not human GUI acceptance.

Windows-only scope for v1.0.0. macOS and Linux artifacts are out of scope for
this release. Signing (QF-001 / G25) is tracked separately in
``packaging/WINDOWS-SIGNING.md`` and is **not** closed by anything in this pack.

Recording rules (apply to every gate)
=====================================

#. Use a disposable project or the generated acceptance fixture. No production
   repository, customer data or credentials.
#. Use a dedicated, low-limit, **revocable** test key, entered through Settings.
   Never paste it into a terminal, report, screenshot, issue or chat message.
#. Record the **artifact hash**, machine/OS, date, provider and model for every
   run. A result without an artifact identity is not evidence.
#. Scrub logs: remove keys, prompts containing secrets and full production
   paths. Record a short excerpt, not a full transcript.
#. A stop condition (workspace escape, approval bypass, key in UI/log, data
   loss, install damage, crash during approval) means: stop, preserve the log,
   notify the coordinator, record ``FAIL``.
#. Do not count a test as passed if the tester only repeated automated checks.
#. Every ``FAIL`` needs a triage decision: fixed in a named build, accepted as a
   documented limitation, or blocking release.

Common run identity (copy into every gate)
------------------------------------------

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Field
     - Value to record
   * - Gate / test ID
     - e.g. ``QF-003 / GUI-04``
   * - Reviewer (name)
     - Named human; not the build operator for independent gates
   * - Date / time (UTC)
     - ``YYYY-MM-DDTHH:MMZ``
   * - Artifact + SHA-256
     - Exact MSI or executable hash under test
   * - Build commit / version
     - e.g. ``506f78a`` / ``0.9.0`` (candidate version when available)
   * - Machine / OS
     - Host or VM identifier; Windows 11 x64 build number
   * - Provider / model
     - Real provider and model, or local endpoint (QF-002 only)
   * - Result
     - ``PASS`` / ``FAIL`` / ``BLOCKED`` / ``NOT TESTED``
   * - Evidence ref
     - Scrubbed log excerpt id, screenshot id, or recording location
   * - Triage decision
     - Required only for ``FAIL``
