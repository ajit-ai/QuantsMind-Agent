What v0.2 is
============

v0.1 could read a project. v0.2 lets it **change** one -- and keeps the same
central rule the rest of the application is built on:

   The LLM may propose actions, but the application remains responsible for
   authorization and execution.

The agent can now write files, apply deterministic edits, delete files, run
approved commands and inspect Git state. Every one of those is a separate,
individually decided operation. Deleting a file and running a command always
reach the user, whatever else the settings allow, and can never be granted for
the session; anything the command safety policy forbids is refused before the
user is asked at all, because offering "Allow" for it would turn the dialog into
a speed bump rather than a control.

    Windows 11 user
          |
    QuantsMind-Agent GUI
          |
    Workspace -> Agent Core -> Model Gateway -> real LLM
                      |
              Tool Registry  <- enforcement point
                      |
        +-------------+-------------+
        |             |             |
   Permissions   Command policy   Workspace containment
        |             |             |
        v             v             v
   Allow/Deny     Block/Allow   path validation
   (human)        (structural)  + symlink defence

New capabilities
================

Filesystem
----------

.. list-table::
   :header-rows: 1
   :widths: 22 78

   * - Tool
     - Behaviour
   * - ``write_file``
     - Create or replace a text file. Parent folders are created only when the
       call explicitly authorises it.
   * - ``edit_file``
     - One deterministic edit (``replace``, ``replace_all``, ``insert_before``,
       ``insert_after``, ``replace_lines``, ``append``, ``prepend``) with an
       explicit precondition.
   * - ``delete_file``
     - Remove a single file. Always asks. Never removes a directory tree.
   * - ``undo_file``
     - Put one file back the way it was before the newest change the agent made
       to it. Always asks. Restores the previous bytes exactly, removes the file
       when the change being undone created it, and refuses when the file
       changed outside the agent. ``delete_file`` is deliberately not undoable.

Structured diffs
----------------

``write_file`` and ``edit_file`` report what they changed, not only that they
changed something. The result the model reads back carries a unified diff, the
number of lines added and removed, and whether the diff was truncated:

.. code-block:: text

   diff          +DEFAULT_PORT = 9090
                 -DEFAULT_PORT = 8080
   diff_kind     modified
   diff_added    1
   diff_removed  1
   diff_truncated false

``diff_kind`` names the cases where there is nothing to compare: ``created``
when the file did not exist before, and ``unavailable`` when the previous
content exists but was too large to read. ``delete_file`` reports no diff at all
-- the file it changed no longer has content to compare against.

The diff is bounded so a whole-file rewrite cannot flood the context: at most
200 lines and 8000 characters. The line counts always describe the whole change,
so they stay usable as a summary even when the text is cut short.

Reversible changes
------------------

``write_file`` and ``edit_file`` record a pre-image in a session-scoped undo
list: a stack per file, holding the exact bytes and a SHA-256 digest. One
``undo_file`` call reverses one step, so successive changes to one file can be
walked back one at a time, and files can be undone independently of each other.

The list lives in memory for the current conversation only. A new conversation,
a different project, or closing the application discards it. A write that failed
records nothing, and an undo that failed leaves its step available to retry.

Command execution
-----------------

``run_command`` runs one development command inside the project folder after
approval, with a working-directory containment check, a timeout, cancellation,
bounded stdout and stderr, and the exit code reported back to the model. Both
streams are capped from both ends -- the head and the tail of the output are
kept, with a marker where the middle was dropped -- because the part of a
failing command that matters is usually its last line.

Git awareness
-------------

``git_status``, ``git_diff`` and ``git_log`` report branch, staged/unstaged/
untracked state, line-level changes and recent commits. All three are
structurally read-only: see :ref:`git-read-only`.

Approvals
=========

By default, any tool that can change the machine or the workspace prompts first.
The prompt shows the operation, the target, the workspace and the arguments.
Two more fields depend on the tool: ``run_command`` also shows the one-line
reason the model gave and the risk classification of the command, because those
exist only for commands -- the other tools have no reason argument to show.

Two settings relax the default, and neither relaxes it completely:

* **Auto-approve reads** skips the prompt for reading, which cannot change
  anything. It is on by default; turning it off turns workspace reads into
  ``ASK`` decisions, which degrade to ``DENY`` without an approver.
* **Auto-approve writes** skips the prompt for ``write_file`` and ``edit_file``
  only, and is off by default. ``delete_file``, ``undo_file`` and
  ``run_command`` keep asking whatever this is set to, and ``NETWORK`` stays
  denied.

A headless run -- the CLI, the tests, a start with no window attached -- has
nobody to ask, so every prompt resolves to a denial and nothing mutating runs
unattended.

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Decision
     - Meaning
   * - Allow / Allow Once
     - Run this one call only.
   * - Allow for Session
     - Allow every later call of the same tool until the conversation, project
       or settings change. Never offered for ``delete_file`` or ``undo_file``.
   * - Deny
     - Do not run. The tool returns a failure the model can react to, and the
       turn continues.

A denial is a failed observation, not a crash: the agent is told and may try
something else. Escape or closing the window denies.

What did not change
===================

* The permission layer is still the only enforcement point. A tool never
  checks its own permissions, so a mis-annotated tool cannot bypass policy.
* Path containment is still one implementation
  (:meth:`~quantsmind_agent.workspace.Workspace.resolve`), shared by reads and
  writes.
* The agent loop is still bounded, interruptible and recoverable.
* Git mutations are still absent. ``commit``, ``push``, ``checkout``, ``reset``,
  ``merge`` and ``rebase`` are blocked even through the generic command tool.

Known limitations
=================

**Application-level command policy is not an OS sandbox.** It is a deny list
evaluated by this process. A permitted interpreter can spawn children, read
environment variables or invoke another program, and approving a command means
approving that program, not a verified effect. Real isolation needs OS-level
mechanisms -- containers, job objects, a low-privilege account -- and none of
those are in scope for v0.2.

**Cancellation stops the direct child only.** Windows has no portable
process-tree kill, so a command that spawned grandchildren may leave them
running.

**Delete is file-only.** Removing a directory tree is irreversible at a scale an
approval dialog cannot meaningfully display, so it is deferred.

**The undo list is per session and per file.** It does not survive a restart, it
never crosses a project boundary, and it holds the pre-images it needs in memory,
so a file too large to keep is written without a reversible step recorded. It
also cannot reconstruct anything the agent did not write through the tools: a
file deleted with ``delete_file``, or edited by another program, is outside it by
construction.

**Diffs are bounded and lossy for display.** The text is capped at 200 lines and
8000 characters, and content that is not valid UTF-8 is decoded leniently for
the diff even though the undo journal stores the exact bytes. ``write_file``
replacing an entire large file therefore produces a summary, not a full patch;
reading the file is how the model sees more.

See :ref:`architecture-security-boundaries` for the full list.
